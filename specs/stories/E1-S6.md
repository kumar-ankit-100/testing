# E1-S6: Auth login endpoint

**Epic:** E1 — Platform Foundations
**Layer:** API
**Group:** F
**Depends on:** E1-S4, E2-S1

## Description

`POST /api/auth/login` — the endpoint `api-contracts.md` has always documented and that `E1-S4`'s auth dependencies (`require_role`, `current_principal`) and `E3-S3`'s admin router have assumed exists since Group D, but which no story ever built. Closes that gap: validates seeded demo credentials (or, for a subscriber, a mobile number) and returns a signed JWT with role + subject claims, satisfying NFR-04 (subscribers may only access their own data).

## Acceptance Criteria

1. **Given** valid seeded credentials for a staff role (CSR or ADMIN), **when** `POST /api/auth/login` is called with `{"username": ..., "password": ...}`, **then** the response is HTTP 200 with an `access_token` whose decoded claims carry that role and a subject identifying the user — reusing `auth_service.create_access_token`/`decode_access_token` exactly as `E1-S4` already established, not a second token format.
2. **Given** a subscriber's mobile number with no prior registration, **when** `POST /api/auth/login` is called with `{"mobile_number": ...}`, **then** the response is HTTP 200 with a pre-registration token (`subscriber_id: null` in the response body, per `api-contracts.md`'s documented login contract).
3. **Given** invalid staff credentials (wrong password or unknown username), **when** `POST /api/auth/login` is called, **then** the response is HTTP 401 with a single generic reason code (`UNAUTHENTICATED`) that does not reveal whether the username exists (no user-enumeration signal — same error and message for "unknown user" and "wrong password").
4. **Given** the application has started, **when** the `users` table is queried after schema apply, **then** exactly one seeded demo user exists for each of `CSR`, `ADMIN`, and `DEALER` roles, with `password_hash` populated via a real hashing function (never a plaintext password column) — synthetic/dummy credentials only, consistent with the Synthetic-Data Rule already governing dealer/plan seed data.
5. **Given** a login attempt, succeeding or failing, **when** it is logged, **then** the log entry never contains the raw password and never contains an unmasked mobile number — reusing `logging_service`'s existing `PII_FIELD_NAMES` masking (NFR-03/NFR-06), not a new masking path.
6. **Given** a valid subscriber JWT issued by this endpoint for subscriber A, **when** that token is used against an endpoint scoped to subscriber B's data, **then** the response is HTTP 403 — exercising `E1-S4`'s existing `require_own_subscriber` dependency end-to-end through a token this endpoint actually issued, not a test-minted one.

## Notes

- This story also requires updating the integration tests written for `E1-S4` and `E3-S3` (already evaluator-approved, Groups B and D) to obtain their bearer tokens through this real endpoint rather than minting them directly via `auth_service.create_access_token()`. Keep the direct-mint helper only where a unit test is deliberately isolating a single dependency (e.g. `test_auth_service.py` itself) — every *integration* test exercising a router should go through `POST /api/auth/login` once this story lands, so the suite actually proves the endpoint works rather than assuming it.
- `E2-S5` (Group F, not yet implemented) gains a login page + role-based route guard in its own story scope as part of this fix — see the amended ACs in `specs/stories/E2-S5.md`.
