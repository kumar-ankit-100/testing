# Business Case — TelcoLane (BC-AINE-020)

## Problem

A telecom operator wants to consolidate subscriber and plan management into a single platform — handling activations, plan upgrades/downgrades, suspensions, pro-rata billing, and port-out workflows — under one constraint: no manual coding. All external integrations (network provisioning, MNP backend, payment gateway, real KYC) are stubbed; every line of production code is generated by Claude Code agents under human supervision.

The risk being modeled is not a real business loss (this is an evaluation project with synthetic data and no real users or money) but the risk of failing to demonstrate AI-native delivery competence: accurate pro-rata billing, audited state transitions, port-out compliance, and process discipline (tests, PR-driven merges, CI), as graded by the capstone's 21-parameter rubric.

## Target Users

| Role | Context | Interface |
|---|---|---|
| **Subscriber** | Self-service, low technical assumption | React web UI — register, view activation status, change plan, suspend/resume, port-out |
| **CSR** (Customer Service Representative) | Internal back-office user, resolves exceptions | Desktop-first internal UI — override rejected activations/plan-changes, terminate subscriptions |
| **Admin** | Internal back-office user, manages catalog and reporting | Desktop-first internal UI — plan catalog CRUD, activation funnel/churn/plan-mix/ARPU dashboards |
| **Dealer** | Identified only at activation time (dealer-code validation against a seeded master) | No UI — no story in this build ever defined a dealer-facing portal; the role exists at the auth/type level so authorization tests can exercise 403s against it |

All roles authenticate via `POST /api/auth/login` (seeded demo credentials for staff roles; mobile-number-only self-service for subscribers) and are authorized at the controller layer. Subscribers see only their own subscription data.

## Success Metrics

Since this is a graded evaluation project rather than a live product, success is measured by:
- All 10 functional acceptance criteria (AC-01–AC-10) and all 8 non-functional requirements (NFR-01–NFR-08) implemented and independently verified (not self-reported) before being marked done — the Generator→Evaluator ratchet loop this project's harness runs on.
- A working, one-command-runnable application with seed data (plan catalog, seeded demo users/dealers), not just passing unit tests in isolation.
- Zero regressions introduced while closing gaps found mid-build: every fix to already-approved code (the auth-login gap, the CSR/termination/reporting API gap) was verified against the full existing test suite before being accepted, not just the new code path.
- A git history that is itself evidence of the process: every change via a feature branch merged `--no-ff`, no direct commits, sprint contracts and evaluator reports committed alongside the code they verify.

## Domain Rules (the ones that actually drove design decisions)

- **Money is `Decimal`, never `float`**, end to end — pro-rata calculations, plan prices, billing records. SQLite has no native decimal type, so amounts are stored as canonical `TEXT` (`str(Decimal(...))`) and reconstructed on read, avoiding float round-trip drift.
- **Append-only history, enforced at two levels**: the repository layer exposes no `update_*`/`delete_*` function for plan versions (once published), state transitions, billing records, port-out events, or CSR overrides — and a SQLite `BEFORE UPDATE`/`BEFORE DELETE` trigger backstops that as defense-in-depth against a raw-SQL bypass.
- **One shared FSM, not per-service transition logic.** Every service that moves a subscription between states (activation, suspend/resume, port-out, termination, CSR override) calls the same declarative transition table, so "is this move legal" has exactly one authority, not five duplicated `if` chains.
- **PII masking is structural, not a convention.** All logging goes through one `logging_service` module that masks mobile numbers, Aadhaar references, and PAN references before serialization — there is no code path that can "forget" to mask, because nothing outside that module performs raw log serialization.
- **CSR overrides are a re-run, not a bypass.** The override service doesn't flip state directly — it re-invokes the same authoritative activation/plan-change service function with only the one specific failed rule suppressed, so the FSM and append-only writes still go through their single normal code path. Every override attempt, successful or not, is written to an audit table with actor, reason code, and timestamp.
- **A password is never the comparison target, even on the "user doesn't exist" path.** Login checks a precomputed dummy hash when the username is unknown, so `verify_password()` always runs — closing the timing side-channel between "wrong password" and "no such user," not just the response-shape one.

## Value Proposition

A rubric-graded demonstration that an AI-Native Engineer — acting as architect, supervisor, and quality gatekeeper rather than hand-coder — can deliver a correctness-sensitive, audited, financially-exact telecom subscriber lifecycle platform end to end: specs first, implementation generated and independently re-verified (not self-graded) against those specs, gaps found during that verification fed back into the spec and closed through the same process, and every change traceable through a PR-driven git history.
